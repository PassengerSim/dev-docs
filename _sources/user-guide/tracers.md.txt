# Tracing

In addition to the completely flexible `callback` data storage system, PassengerSim also includes
the ability to "trace" certain details of the simulation. Traces are more aggregate than other
callbacks, as they will follow the average values of various measures over many samples. Unlike
other aggregate measures, they allow for the selection of a limited number of micro-level details,
e.g. path forecasts for specific paths, or bid prices on specific legs. This contrasts with the
database functionality, which can (relatively) efficiently store this information for *all* paths or
legs. Tracing allows the analyst to probe a simulation for details of interest without becoming
bogged down in the recording and storage of massive amounts of data that really isn't needed.

```{code-cell} ipython3
import passengersim as pax

pax.versions()
```

Here, we'll run a quick demo using the "3MKT" example model. We'll give AL1 the 'P' RM system to
make it interesting.

```{code-cell} ipython3
cfg = pax.Config.from_yaml(pax.demo_network("3MKT"))

cfg.simulation_controls.num_samples = 400
cfg.simulation_controls.burn_samples = 50
cfg.simulation_controls.num_trials = 1
cfg.db = None
cfg.outputs.reports.clear()
cfg.outputs._write_no_files()

cfg.carriers.AL1.rm_system = "P"

sim = pax.Simulation(cfg)
```

## Forecast Tracing

The path forecast tracing capabilities allows us to record detailed data about a subset of
Simulation path forecasts, so we can review them after the simulation. The tracing will summarize
the average forecasts for the specific paths, but will not store the sample-by-sample forecast
details, which would be an enormous amount of detail that will require large amounts of memory or
disk storage and may not be sufficiently useful for analysis. A similar tracing tool is available
for leg forecasts as well.

```{code-cell} ipython3
from passengersim.tracers.forecasts import (
    PathForecastTracer,
    fig_path_forecast_dashboard,
)

f_tracer = PathForecastTracer(path_ids=[1, 5, 9])
f_tracer.attach(sim)
```

The path tracer also records the adjusted fare for each booking class and timeframe, so you can
review adjusted fares without recording the simulation database. Values match the `adjusted_price`
column of the [`path_forecasts`](summary-tables/forecasts.md) table: when a carrier does not use
fare adjustment they are plain fares, and a class is missing for timeframes after its advance
purchase restriction closes it. The tracer reads them once per sample, at the start of the sample,
so an RM step you write that changes adjusted fares later in the sample would not be captured. Leg
forecast tracing does not include adjusted fares.

## Bid Price Tracing

The native summary covering **every leg** is enabled by default.

After running, access `summary.leg_bid_price_history`. It is indexed by `(leg_id, days_prior)` and
contains:

| Column              | Meaning                                              |
| ------------------- | ---------------------------------------------------- |
| `bid_price_mean`    | Mean bid price across retained samples and trials    |
| `bid_price_std_dev` | Pooled sample standard deviation                     |
| `n_observations`    | Number of retained observations for that leg and day |

```python
summary = pax.Simulation(cfg).run()
daily_prices = summary.leg_bid_price_history
one_leg = daily_prices.xs(101, level="leg_id")
```

Collection includes each integer day from the earliest configured DCP through departure day,
excludes burn-in, and works with `cfg.db = None`. It is on by default; the table is `None` when
collection is disabled. Set `collect_leg_bid_prices: false` before the next run to turn it off. The
option always collects all legs; filtering the resulting table does not reduce collection. A cell
with no observations has a missing mean and standard deviation; a single observation has a missing
standard deviation. The native collector stores online statistics rather than individual sample
observations, and saved PXSIM and pickle results retain the information needed to combine summaries
correctly.

Native collection follows core daily-statistics timing and the existing leg reporting-price
convention, including sold-out legs. For positive `days_prior`, recording occurs at the core daily
or DCP event; later callbacks can subsequently change prices. At `days_prior == 0`, recording occurs
at the end of the sample, after the event queue finishes. The native collector has no callback
priority setting, so a Python tracer may observe different prices if callbacks change them between
these times. Multi-cabin legs record their leg-level reporting price without selecting a cabin or
applying cabin capacity-sharing rules.

Each row pools individual observations across retained samples, trials, and workers. The standard
deviation is the sample standard deviation of those observations (`ddof=1`), including variation
between trials. It is not the average of trial standard deviations. Rerunning a simulation starts a
fresh history; saved summaries retain their previous results. This table requires no database report
selection.

You can use native collection alongside `LegBidPriceTracer`. Use the Python tracer below when
selecting only some legs or developing custom collection behavior. It pools its statistics across
trials and workers in the same way. Cabin-level collection is not yet enabled by this option.

### Selected legs and paths

Similarly, the bid price tracing feature allows us to record detailed data about a subset of
Simulation bid prices. We can record bid prices by leg, path, or both if desired. Each tracer only
attaches to the bid prices on a selected subset of individual legs, so as to not overwhelm the
simulation with data.

```{code-cell} ipython3
from passengersim.tracers.bid_price import (
    LegBidPriceTracer,
    PathBidPriceTracer,
    fig_leg_bid_prices,
    fig_path_bid_prices,
)

bp_tracer = PathBidPriceTracer(path_ids=[1, 5, 9])
bp_tracer.attach(sim)

leg_bp_tracer = LegBidPriceTracer(leg_ids=[101, 111])
leg_bp_tracer.attach(sim)
```

## Segmentation Tracing

The segmentation tracer records cumulative sales **and realized revenue** at each DCP, by carrier,
market, booking class, and passenger segment. It provides the same information as the
database-backed [`segmentation_detail`](summary-table-segmentation-detail) table, plus revenue,
without using the database. You can limit it to selected markets (and, optionally, carriers) to keep
the recorded data small on large networks. Markets are directional, and can be given as
`(orig, dest)` tuples or as strings like `"BOS-LAX"`.

```{code-cell} ipython3
from passengersim.tracers import SegmentationTracer

seg_tracer = SegmentationTracer(markets=["BOS-LAX", "BOS-ORD"])
seg_tracer.attach(sim)
```

Once the tracers have been attached, we run the simulation as normal. The attached tracers will
automatically collect and aggregate the relevant data, and attach the tabulated results to the
summary outputs.

```{code-cell} ipython3
summary = sim.run()
```

All the usual summary data remains available for review and analysis.

```{code-cell} ipython3
summary.fig_carrier_revenues()
```

```{code-cell} ipython3
summary.fig_fare_class_mix()
```

The segmentation tracer results are averaged per sample across all non-burned samples in all trials.
They are available as `summary.segmentation_detail_traced`, indexed by carrier, market, booking
class, segment, and days prior, with `sold` and `revenue` columns holding cumulative values through
each DCP.

```{code-cell} ipython3
summary.segmentation_detail_traced.head()
```

The usual segmentation figure uses tracer data when it covers the requested scope, and can show
revenue as well as bookings. With a filtered tracer, select a covered market (and carrier, if
filtered). Broader booking requests fall back to database data; revenue requests outside tracer
coverage raise `ValueError`.

```{code-cell} ipython3
summary.fig_segmentation_detail(metric="revenue", orig="BOS", dest="LAX")
```

The `segmentation_detail_traced` function can reshape the table, converting cumulative values into
values within each timeframe, and pivoting segments into columns.

```{code-cell} ipython3
from passengersim.tracers.segmentation import segmentation_detail_traced

segmentation_detail_traced(summary, timeframe=True, wide=True).head()
```

## Tracers in Callback Data

All the underlying data for these reports is stored in the summary's `callback_data` attribute, if
you want to access it to parse or visualize it differently. The forecast tracers contain selected
summary statistics by path or leg, days prior, and fare class. These statistics are aggregated
across all relevant (i.e. non-burned) samples.

```{code-cell} ipython3
summary.callback_data.selected_path_forecasts
```

The bid prices data has three rows for each day prior: the mean bid price of the leg or path
(`mean`), its sample standard deviation (`std_dev`), and the number of observations behind them
(`n`). These are found in the `statistic` level of the index, so select one by name, for example
with `df.xs("std_dev", level="statistic")`.

```{code-cell} ipython3
summary.callback_data.leg_bid_prices
```

The statistics pool every observation across samples, trials, and workers, so a multi-process run
reports exactly the statistics a single-process run of the same trials would. The standard deviation
includes the variation between trials. A day observed only once has a missing standard deviation.

```{note}
Results saved by earlier versions of PassengerSim have no `n` row, and their standard deviation is
the average of each trial's standard deviation, which leaves out the variation between trials.
Combining such a result with a new one gives trial-weighted averages without an `n` row. If the
standard deviation matters to you, re-run the simulation. The tracers' `options_version` has
changed, so a configuration that requires the old version reports an error instead of mixing the
two.
```

## Attaching, Naming, and Re-running Tracers

Calling `tracer.attach(sim)` attaches a fresh copy of the tracer to the simulation, on the lifecycle
hook the tracer is designed for. The tracer object you created is never modified by a run, so you
can attach the same object to several simulations without them sharing any data. The callback
decorator methods also accept a tracer, so `sim.daily_callback(LegBidPriceTracer([101]))` works too,
but only on the tracer's own hook: attaching a begin-sample tracer such as `LegBidPriceArrayTracer`
with `sim.daily_callback` raises a `ValueError` immediately, rather than failing part-way through
the run. If in doubt, use `attach`.

Each tracer's results are stored in `callback_data` under its name, such as `leg_bid_prices`. To
attach two tracers of the same kind to one simulation, for example to trace two groups of legs
separately, give one of them its own name:

```python
LegBidPriceTracer(leg_ids=[101, 102]).attach(sim)
LegBidPriceTracer(leg_ids=[111, 112], name="return_leg_bid_prices").attach(sim)
summary = sim.run()
summary.callback_data.leg_bid_prices  # legs 101 and 102
summary.callback_data.return_leg_bid_prices  # legs 111 and 112
```

Attaching a tracer with a name that is already in use replaces the earlier tracer, with a warning
suggesting the `name=` option. This keeps a notebook cell that attaches a tracer safe to run more
than once: you get one tracer, not two. A name cannot be one of the hook names (`daily`,
`begin_sample`, and so on), which are reserved for ordinary callback data. The plotting functions,
such as `fig_leg_bid_prices`, read the tracer's default name.

Every run starts its tracers empty, so calling `sim.run()` (or `sim.run_trial()`) a second time
gives results for the second run alone, not an accumulation of both. A run that fails part-way
through stores no tracer results, and running it again starts from scratch. Within one run, tracers
accumulate across all of its trials. The built-in tracers ignore burn-in samples.

## Writing a Tracer

A tracer is a subclass of `GenericTracer`. It needs a `name` for its results, a `reset` method that
empties its accumulators, and a `finalize` method that turns them into a DataFrame. It observes the
simulation through one or more hook methods, named for the lifecycle hooks: `on_initialize_sample`,
`on_begin_sample`, `on_daily`, `on_end_sample`, and `on_finalize_sample`. The tracer is attached to
every hook whose method it defines, and a single copy of the tracer receives all of those calls, so
it can compare what it saw at different points of each sample.

This tracer records how many seats each leg sells between the start and the end of a sample:

```python
import pandas as pd

from passengersim.tracers.generic import GenericTracer


class LegSalesTracer(GenericTracer):
    name = "leg_sales"
    skip_burn = True  # The simulation skips burn-in samples for every hook.

    def __init__(self, leg_ids, *, name=None):
        self.leg_ids = list(leg_ids)
        self._set_name(name)  # Optional instance-level result name.
        self.reset()

    def reset(self):
        self.legs = None
        self.at_start = {}
        self.totals = dict.fromkeys(self.leg_ids, 0)
        self.samples = 0

    def setup(self, sim):
        # Look up the legs once per run, so a bad leg ID fails before any sample.
        self.legs = {leg_id: sim.eng.legs.select(leg_id=leg_id) for leg_id in self.leg_ids}

    def on_begin_sample(self, sim):
        self.at_start = {leg_id: leg.sold for leg_id, leg in self.legs.items()}

    def on_end_sample(self, sim):
        for leg_id, leg in self.legs.items():
            self.totals[leg_id] += leg.sold - self.at_start[leg_id]
        self.samples += 1

    def finalize(self):
        mean = {leg_id: total / max(self.samples, 1) for leg_id, total in self.totals.items()}
        df = pd.DataFrame({"mean_sold": mean})
        df.attrs["n_samples"] = self.samples
        df.attrs["aggregation_process"] = "wgt_by_samples"
        return df


LegSalesTracer([101, 102]).attach(sim)
summary = sim.run()
summary.callback_data.leg_sales
```

Hook methods take the same arguments as the corresponding callback functions: the simulation, plus
the days prior to departure for `on_daily`. Like a callback function, a hook method may return a
dictionary to store as ordinary callback data, though most tracers keep what they observe and report
it from `finalize`. A tracer can set a `priority` attribute, which works as it does for a callback:
it is the offset in seconds from each DCP's trigger time. A tracer has just one `priority`, which
applies to all of its queued hook methods (`on_begin_sample`, `on_daily`, and `on_end_sample`), so
the tracer observes every DCP from the same side of the RM systems and the simulation's bookkeeping.
A `priority` given when attaching the tracer, as in
`sim.begin_sample_callback(tracer, priority=-5)`, likewise applies to all of these methods,
whichever registration method was used. When two of a tracer's methods fall at the same moment, they
run in lifecycle order: `on_begin_sample` before the first `on_daily` call of a sample, and the last
`on_daily` call before `on_end_sample`. The same order holds between different callbacks and tracers
that share a moment (after any RM systems, which always run first). A tracer that needs different
timing for different hooks can be split into two tracers.

For each run, the simulation takes the tracer through these steps:

1. `reset()`, once, at the start of the run. A tracer is never reset between the trials of one run,
   so its results cover all of them.
2. The scenario is built: the network, fares, and demands now exist.
3. `setup(sim)`, once. This is the place to look up the legs, paths, or fares the tracer will
   observe, to allocate its arrays, and to report problems before the run gets going. The default
   does nothing.
4. The hook methods, for every trial and sample of the run (skipping burn-in samples, if `skip_burn`
   is set).
5. `finalize()`, once, after the last trial. Its result is stored in `callback_data` under the
   tracer's name.

If `setup` or a hook method raises an exception, the run stops, `finalize` is not called, and no
result is stored. Running again starts over from `reset`. When a multi-process simulation runs, each
worker gets its own fresh copy of the tracer, so no state is shared between workers, or between
experiments.

### Combining results

When a simulation runs in several processes, or results are added together, the tables from each
part are combined. A tracer chooses how by setting `df.attrs["aggregation_process"]` on the table
its `finalize` method returns:

| Process          | Combination                                                                  |
| ---------------- | ---------------------------------------------------------------------------- |
| (none)           | The tables are added together with `+`.                                      |
| `wgt_by_samples` | A mean weighted by `df.attrs["n_samples"]`, as in the example above.         |
| `wgt_by_trials`  | A mean weighted by `df.attrs["n_trials"]`.                                   |
| `pooled_moments` | Exact pooling of the `mean`, `std_dev`, and `n` rows of a `statistic` level. |
| `concat_rows`    | The rows of both tables are stacked, for tables that keep every observation. |

Two tables declaring different processes cannot be combined, and raise an error. A tracer can define
its own process with `passengersim.callbacks.register_combiner`, giving it a function that combines
two such tables into a new one. Register it in the module that defines the tracer, since saved
results only record the process's name: combining saved results in a new session raises an error
naming the process until that module has been imported. Once results using a process exist, never
change what the process name means; choose a new name instead.

### Legacy tracers

Tracers written before hook methods existed set a `hook` class attribute and define `__call__`
instead. They work as before, on that one hook. A tracer uses one form or the other: defining `hook`
together with any hook method is an error.

## Relationship to Callbacks

Unlike other callback data, the tracers are not stored by sample day, as that would generally create
an overwhelming amount of data to store, and we are typically not interested in that much detail. If
we are interested in grabbing and storing path forecast data for individual sample days, we can
still do that with the regular callback interface.

```{code-cell} ipython3
sim1 = pax.Simulation(cfg)
```

```{code-cell} ipython3
@sim1.begin_sample_callback
def grab_forecasts(sim):
    if sim.eng.sample not in [300, 375]:
        return
    return {
        f"path-{p}": sim.eng.paths.select(path_id=p).get_forecast_data()
        for p in [1, 5, 9]
    }
```

```{code-cell} ipython3
summary1 = sim1.run()
```

When run like this, we capture not the average path forecast over the simulation, but rather the
exact path forecast for the selected paths (1 and 9) at sample days 300 and 375. The data is stored
in the `callback_data.begin_sample` attribute:

```{code-cell} ipython3
summary1.callback_data.begin_sample
```

We can review the details of each specific forecast by accessing the dashboard visualization.

```{code-cell} ipython3
summary1.callback_data.begin_sample[0]["path-1"].dashboard()
```

We can also access individual sub-tables of forecast data as pandas DataFrames, to manipulate or
visualize as we like.

```{code-cell} ipython3
summary1.callback_data.begin_sample[0]["path-1"].history_sold_yieldable
```

```{code-cell} ipython3
summary1.callback_data.begin_sample[0]["path-1"].mean_in_timeframe
```

## Native daily path bid-price history

Enable path collection before running:

```python
sim.config.simulation_controls.collect_path_bid_prices = True
summary = sim.run()
path_prices = summary.path_bid_price_history
```

This opt-in table is indexed by `(path_id, cabin_code, days_prior)` and contains `bid_price_mean`,
`bid_price_std_dev`, `augmented_bid_price_mean`, `augmented_bid_price_std_dev`, and a single shared
`n_observations` count. Both prices are recorded together once per retained sample and day,
excluding burn-in. No database or tracer is required. Collection is independent of leg collection
and uses the same daily recording time. Unobserved means and standard deviations are missing; one
observation has an undefined sample standard deviation.

The total is the sum of one-passenger reporting bid prices on the path's legs, using the specified
cabin and the existing finite sold-out reporting convention. The augmented total is the effective
threshold for a reference class, selected as the class with the lowest `fcst_revenue` in that cabin
and a finite adjusted fare at the active carrier timeframe. Strict (`bp`) control requires a
positive adjusted fare; loose (`bp_loose`) control allows zero only when the current total bid price
is zero within `1e-9`. A zero-clipped class can open under loose control when the total bid price is
zero, within the offer check's equality tolerance. Positive adjusted fares remain eligible even when
currently closed: their adjustment still preserves the full markup, whereas clipping destroys that
information. Equal decision prices are resolved by booking code. The reference can change across
time and samples.

```text
augmented total = total + reference fcst_revenue - reference adjusted_fare_price
```

The decision price (`fcst_revenue`) can differ from the price shown to the customer under brand,
matrix, or weighted pricing; they coincide under the default lowest-price rule. When no adjustment
covers the timeframe, the scalar decision-price fallback is used and the markup is zero.

The adjusted fare is read from the same accessor used by offer checks. This includes hybrid
weighting, MR and KI adjustments, the zero floor, and highest-class exemptions. No separate Frat5
markup cache is maintained. Without an adjustment, augmented and total prices are equal. If all
classes in a cabin fail the reference-selection rule (for example, after advance-purchase closure),
the adjustment is zero; no reference offer exists then. This statistic describes the reference
class, not a universal threshold for every fare. Capacity and other availability rules still apply,
and sold-out legs retain their finite reporting price rather than the offer-time sentinel. Offer
checks treat differences smaller than `1e-9` as equality: `bp` closes at equality, while `bp_loose`
opens. Apply that same rule when comparing a reference decision price with its augmented threshold.

Only paths of bid-price-controlled carriers (`bp` or `bp_loose`) are collected. Leg-controlled
carriers are omitted. Cabin groupings are cached until path-class count changes or histories are
reset, including trial boundaries; reset histories after changing cabin assignments in place.

Raw paired moments are retained in saved results and merged by observation count across trials and
workers. This preserves both between-trial variation and the covariance between leg prices.
Disabling collection releases native histories; the summary is `None` when collection is disabled.
Older results without this table remain readable.
